# Архитектура и инженерные решения

## Компоненты

- `web/`: Spring MVC (HTML-секции) и REST API; десериализация DTO, HTTP статусы, CSRF.
- `service/`: правила, транзакции, аудирование, генерация событий, идемпотентность.
- `repository/`: Spring Data JPA; Hibernate строит SQL.
- `model/`: сущности JPA, enum, встроенные координаты.
- `realtime/`: native WebSocket; сервер отправляет только тип, идентификатор, действие после успешной транзакции; клиент сам перечитывает REST API.
- `db/migration/`: Flyway и CHECK/FK/NOT NULL/IDENTITY.
- `config/SecurityConfig.kt`: Spring Security и вход через `UserDetailsService`, читающий PostgreSQL.
- `service/RegistrationService.kt`: нормализация логина, BCrypt, проверка уникальности и регистрационный аудит.
- `templates`, `static`: HTML shell (Thymeleaf) + CSS + JS (без дополнительного frontend toolchain).

## Модель

`Person` содержит `Coordinates` как `@Embeddable`: координаты принадлежат человеку и не переиспользуются. `Location` — настоящая JPA entity (у неё есть идентификатор и отдельное CRUD), отношение `Person -> Location` `@ManyToOne`, nullable. Несколько людей могут ссылаться на одну локацию. Удаление локации с зависимостями происходит в одной транзакции с переводом людей на другую локацию, указанную пользователем. Если нет зависимостей, удаление разрешено без замены.

## SOLID

- **S:** контроллер, сервис, репозиторий, аудит и WebSocket выполняют различные задачи.
- **O:** новые операции добавляются в сервисы и API без переписывания entity.
- **L:** не строим искусственных иерархий; наследование отсутствует.
- **I:** сервисы зависят только от необходимых repository-интерфейсов.
- **D:** конструкторное DI через Spring, без ручного создания репозиториев и инфраструктуры.

## ACID / транзакции

- **Atomicity:** `@Transactional` связывает изменения людей/локаций, аудит и записи ключей идемпотентности. При ошибке — rollback.
- **Consistency:** Jakarta Validation на DTO, проверки в сервисе (включая `isFinite()`), CHECK/NOT NULL/FK в PostgreSQL, `ddl-auto: validate`.
- **Isolation:** применяется default PostgreSQL `READ COMMITTED`; version (`@Version`) плюс явно передаваемый `version` в PUT предотвращают потерянные изменения. Для высококонкурентной операции удаления по весу при строгом требовании «один выбранный объект» следует рассмотреть блокировку строки/`FOR UPDATE`; текущая реализация полагается на конфликты конкурирующих транзакций.
- **Durability:** PostgreSQL commit до рассылки события.

## Идемпотентность

- `GET` — безопасное чтение.
- `PUT /api/people/{id}`: повтор с **устаревшей версией** вернёт 409. Итоговое состояние не изменится повторно, хотя HTTP-ответ отличается. Оптимистическая проверка нужна для защиты от конкурентных исправлений.
- `DELETE /api/people/{id}` и `DELETE /api/locations/{id}`: повтор не делает новых изменений, возвращает 204.
- Создание Person и удаление **одного по весу**: обязательный `Idempotency-Key`; запись хранится в PostgreSQL в **той же транзакции**, что и действие. Повтор с тем же актором/ключом/параметрами возвращает исходный id и `replayed: true`, не повторяя побочный эффект. Другой запрос с уже использованным ключом получает 409. Параллельные запросы с одним ключом могут получить конфликт уникального ограничения; повтор после завершения транзакции вернёт старый результат. Доступно для одного экземпляра сервера при общей PostgreSQL.
- `POST /api/locations` пока не поддерживает ключ идемпотентности: повторное создание действительно создаёт новую локацию. Это явно оставленное ограничение учебной реализации.

## Coroutines и Immutability

Spring MVC + JPA/Hibernate работают через блокирующие JDBC вызовы. `suspend`-функции не делают эти вызовы неблокирующими, поэтому **coroutines здесь намеренно не используются**. В дальнейшем они уместны при асинхронных внешних I/O и соответствующем стеке (WebFlux/R2DBC или отдельные асинхронные API).

DTO реализованы как immutable Kotlin `data class` с `val`. JPA entities используют `var` и открытые классы (плагины Kotlin JPA/allOpen), потому что этого требует работа ORM, persistence context и dirty checking.

## Аудит / логирование

- `person_lab_audit`: кто, когда, что и с какими данными создал/обновил/удалил. Запись в той же транзакции, что и операция.
- SLF4J INFO по изменению сущностей (actor / kind / id / action); в логах **нет SQL паролей**.
- Операционный лог в `logs/orbis.log` на сервере через `nohup`. Нужна ручная/автоматическая ротация при долгой работе.
- `@TransactionalEventListener(AFTER_COMMIT)` предотвращает рассылку событий о неуспешно сохранённых изменениях.

## Безопасность и ограничения

- Spring Security session-based login; саморегистрация по логину и паролю, без почты. Пользователи в таблице `person_lab_users`, пароль сохраняется только как BCrypt-хеш. Уникальность логина проверяется сервисом и ограничением PostgreSQL, логины приводятся к нижнему регистру. Две демонстрационные учётные записи автоматически создаются только в `local`. На сервере саморегистрация открыта всем, у кого есть доступ к странице; в публичной сети рекомендуется HTTPS и защита от массовой регистрации/подбора паролей. Сброса пароля и ролей администратора пока нет.
- CSRF-защита включена, frontend получает token через Thymeleaf meta.
- Отправляемые WebSocket-события минимальны и не содержат персональные данные. Handshake HTTP доступен только аутентифицированным пользователям и same-origin.
- Нет многосерверного брокера уведомлений: каждый экземпляр держит собственный список WebSocket сессий. Для нескольких экземпляров потребуется Redis pub/sub, RabbitMQ или аналог.
- Журнал аудита доступен обоим авторизованным пользователям; в реальной системе потребуются роли/разграничение доступа, retention и отдельная защита истории.
- При работе на вузовском сервере использовать приватный SSH-туннель или согласованный HTTPS-прокси.


## HTML-маршруты и страницы объектов

В приложении принят **один** способ рендеринга карточек — общий Thymeleaf-шаблон `app.html`
плюс JavaScript-клиент, обращающийся к REST API. Это не серверный рендеринг JPA entity в шаблоне.

HTML-контроллеры разделены по областям (`PeoplePageController`, `LocationPageController`,
`HomePageController`, `UtilityPageController`). Возврат общего шаблона централизован типобезопасным
`AppScreen`, чтобы JavaScript и Kotlin использовали согласованные значения `data-mode`.

При GET `/locations/{id}` MVC-контроллер проверяет существование локации через сервис.
При отсутствии записи `PageErrorAdvice` возвращает HTTP 404 и HTML `error/404`, в то время как
`LocationApi` продолжает возвращать JSON-ошибку для `/api/locations/{id}`. Аналогично для человека.
Контроллер не обращается непосредственно к репозиторию. Никакие SQL-запросы не выполняются в UI.

Текущая карточка выполняет отдельный API-запрос после загрузки HTML, что даёт небольшое повторное
чтение БД, но предотвращает ложный HTTP 200 для удалённого объекта и сохраняет единообразную
JavaScript-архитектуру остальных экранов. Позднее это можно оптимизировать, но сейчас переход на
серверный Thymeleaf-рендеринг карточки создал бы две конкурирующие модели отображения.
